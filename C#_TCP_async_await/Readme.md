# C# TCP async/await 기반 소켓서버
```async/await``` 기반의 비동기 소켓서버이다. <br/>

## Task
일단 ```AcceptLoop```를 ```Task```로 작성하여 항상 돌아가게 만든다. <br/>
이후 ```AcceptAsync```로 소켓을 반환받으면 해당 소켓에 대한 수신동작을 수행할 ```RecvLoop```를 ```Task```로 작성한다. <br/>
즉, 기본적으로 ```Accept```를 하기위한 ```Task``` 하나, <br/>
각 클라이언트마다 수신을 담당할 ```Task``` 하나씩을 할당한다. <br/>

그리고 혹시 서버로직이 서버 내에서만 동작하는게 아니라 DB 등 외부에도 반영될 수 있으므로, <br/>
진행중이던 수신처리가 끝나기 전에 프로세스가 종료되지 않도록, <br/>
```RecvLoop```에 대한 ```Task```들을 ```ConcurrentDictionary```에 넣고, <br/>
서버 종료 전에 해당 ```Task```들이 종료되는 것을 안전하게 대기한다. <br/>

## 비동기락
일단 기본적으로 ```await``` 동작을 포함하는 경우 ```lock```을 사용할 수 없다. <br/>
```lock```의 소유권은 스레드가 갖는다. <br/>
하지만 ```await```를 만나 해당 동작이 바로 수행될 수 없는 경우, <br/>
스레드는 idle상태로 진입하지 않고, ```Task```객체에 진행상황을 기록한 후 다른 작업을 수행한다. <br/>
즉, 두개 이상의 실행흐름을 같은 스레드에서 진행하게 될 수 있다는 얘기다. <br/>

이런 경우 서로 배제되어야할 실행흐름들이 임계영역에 같이 진입하게 되어, <br/>
동기화가 깨져버리게 되니 ```async/await```환경에서 사용할 수 있는 비동기락을 활용해야한다. <br/>

```SemaphoreSlim```을 사용해 구현할 수 있으며, 락을 획득할 때까지 대기할 수도 있고, <br/>
획득하지 못했을 때 bool값으로 false를 반환받을 수 있는 함수도 있다. <br/>
전자는 반환값 ```Task```, 후자는 ```Task<bool>```이다.

## 동기화요소
일단 슬라이드버퍼에 ```Enqueue```, ```Dequeue```, ```Pop```에 대해서는 비동기락을 통해 상호배제할 수 있도록 하였다. <br/>
버퍼 내 데이터가 직접 변동되는 동작이기 때문. <br/>
단순히 읽기만 하는 ```Peek```(수신한 스트림의 헤더부분만 읽어 처리할 수 있는 길이가 되었는지 확인용)이나 ```GetMsg```(Peek을 통해 확인한 길이를 바탕으로 처리할 수 있는 메시지가 있다면 ```ArraySegment<byte>```로 반환)의 경우는 락을 쓰지 않았다. <Br/>

수신과정에서는 하나의 클라이언트당 하나의 실행흐름만 수신 및 처리를 담당하기 때문에 특별히 락이 필요한 지점은 없지만, <Br/>
송신과정에서는 다수의 실행흐름이 동시에 하나의 클라이언트에 접근할 상황(타유저로부터의 정보전달 등)이 발생할 것이기 때문에 락을 사용하였다. <Br/>
송신버퍼에 담는 동작은 버퍼 자체의 락을 통해 동기화하기 때문에 다른 실행흐름이 송신중이어도 데이터를 추가로 담을 수 있지만, <br/>
송신함수를 호출하는 건 동시에 한 실행흐름만 접근할 수 있도록 하였다. <br/>
(물론 해당 실행흐름은 송신함수가 끝날때마다 송신버퍼를 확인하고 송신할 내용이 있다면 지속적으로 송신한다.)

## 기존 C++서버와 달랐던 점
C++에서 L7버퍼가 가득차 송신이 불가능한 상태를 해결하기 위해 ```Job```객체를 만들고, ```JobQueue```에 재삽입하여 지속적으로 재시도하는 로직을 구현했었음. <br/>
하지만 ```async/await``` 기반에서는 ```Task``` 자체가 ```Job```객체의 역할을 대신하기 때문에, <br/>
별도로 큐잉할 필요 없이 ```await```로 잠시 쉬는 로직만 넣어줘도 충분했다. <Br/>
C++에서 L7버퍼가 가득찼다고 스레드 자체를 쉬게만든다면 스레드는 점유되어 있는 상태로 기다리기 때문에 성능이 저하되는 부분이 있음. <br/>
하지만 ```async/await``` 기반에서는 ```await Task.Delay()```와 같이 잠시 실행흐름을 멈추더라도, 스레드는 다른 동작을 수행하고 있기 때문에 비교적 성능이 덜 저하되었음.<br/>
